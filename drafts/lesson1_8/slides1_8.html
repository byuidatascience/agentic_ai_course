Lesson 1-8: Memory from Scratch

Threads, long-term memory, and whose memory is whose

Seven stages

Stage The complaint What we build
0 (the baseline) an agent with no memory
1 “You forgot what I said a second ago” one thread: a list of messages
2 “I want separate conversations” many threads: a dict of lists
3 “You forgot me when I started a new chat” long-term memory: a remember tool + a prompt
4 “Now my roommate uses it too” (no new code) the shared memory leaks
5 “Ben shouldn’t see Ana’s memories” memory namespaced by user
6 “What do you actually know about me?” one memory file per user, via the filesystem MCP server

Each stage fixes the problem the last one exposed. Stages 2 and 5 end with the framework version.

  • Notebook: drafts/lesson1_8/memory_from_scratch.ipynb. Same order as the slides.
  • The thread through the whole lesson: the model is stateless. “Memory” is always just what the app decides to send.

Stage 0: No Memory

Every call starts from nothing

  • Ask before the fragment: “Will the second call know her name?”
  • The model is a function: messages in, message out. Nothing persists between calls.

Stage 1: One Thread

A conversation is a list we resend

  • Point at turn 3: the first message gets paid for three times.

thread = []

    new_messages = result["messages"][len(thread):]   # what the agent added this turn

show(thread): that list is the memory.

  • Why [len(thread):]? invoke returns our messages plus whatever it added (AI replies, and later, tool calls). We keep only the new ones.

Stage 2: Many Threads

One list can’t tell conversations apart

  • Ana did homework, then came back the next day for her project and wanted a fresh chat.
  • Three costs of one list: distraction (old material), tokens (resent every turn), and no way back to “just the homework.”
  • Fix: name each conversation. That name is the thread ID.

Stage 3: Long-Term Memory

Two halves: write and read

  • Some facts are about Ana, not about one conversation. They live outside every thread.
  • Write: something has to decide a fact is worth keeping. We let the model decide.
  • Read: saved facts must reach the model. We put them in the system prompt, every turn, every thread.

Stage 3: the tool and the prompt

memories = []   # lives outside every thread


@tool
def remember(fact: str) -> str:
    """Save a lasting fact about the user (name, classes, preferences, goals) for future conversations."""
    memories.append(fact)
    return "Saved."


BASE_PROMPT = (
    "You are a helpful tutor. When the user tells you something lasting about themselves, "
    "call the remember tool to save it."
)


def build_system_prompt(facts):
    if not facts:
        return BASE_PROMPT
    return BASE_PROMPT + "\n\nWhat you remember about the user:\n" + "\n".join(f"- {f}" for f in facts)

Write = the tool. Read = build_system_prompt.

Stage 3: the chat loop

memory_agent = create_agent(MODEL, tools=[remember])
threads = {}


def chat(thread_id, text):
    history = threads.setdefault(thread_id, [])
    history.append(HumanMessage(text))

    # Read: rebuild the system prompt from memory every turn. It is NOT saved in the thread.
    system = SystemMessage(build_system_prompt(memories))
    result = memory_agent.invoke({"messages": [system] + history})

    history.extend(result["messages"][len(history) + 1:])   # +1 skips the system message
    return history[-1].text


print(chat("homework", "Hi, I'm Ana. I'm taking DS 250 and I prefer R over Python."))
print(chat("project", "Which language do I like?"))

A brand-new thread knows Ana prefers R. show(threads["homework"]) shows the tool call; show(threads["project"]) doesn’t.

  • Why not save the system message in the thread? Then every thread would carry a stale copy of the facts.
  • In the project thread, the fact arrived through the prompt, not a tool call.

Stage 4: A Second User

One list for everyone

  • Ana’s roommate Ben starts using the same agent. Same code. He opens his own thread.
  • Ask: “His own thread. What will he see?” Separate threads don’t help: memories was never per-thread.

Stage 5: Per-User Memory

Key everything by user

  • Two changes: memories keyed by user, threads keyed by (user, thread) so Ben can’t open Ana’s “homework”.
  • The tricky part: the model must not pick the user. Identity comes from the app (login), not the conversation.

Stage 5: the code

memories = {}   # user_id -> list of facts
threads = {}    # (user_id, thread_id) -> list of messages


def make_remember_tool(user_id):
    @tool
    def remember(fact: str) -> str:
        """Save a lasting fact about the user (name, classes, preferences, goals) for future conversations."""
        memories.setdefault(user_id, []).append(fact)
        return "Saved."

    return remember


def chat(user_id, thread_id, text):
    history = threads.setdefault((user_id, thread_id), [])
    history.append(HumanMessage(text))

    user_agent = create_agent(MODEL, tools=[make_remember_tool(user_id)])
    system = SystemMessage(build_system_prompt(memories.get(user_id, [])))
    result = user_agent.invoke({"messages": [system] + history})

    history.extend(result["messages"][len(history) + 1:])
    return history[-1].text

user_id is in a closure, not the tool’s signature. The model can’t see it or change it.

Framework version: the map

  • Every piece we built has a name. Have students say the left side before revealing the right, if time.

Framework version: tool and prompt

import uuid
from dataclasses import dataclass

from langchain.agents.middleware import ModelRequest, dynamic_prompt
from langchain.tools import ToolRuntime
from langgraph.store.memory import InMemoryStore


@dataclass
class Context:
    user_id: str


@tool
def remember(fact: str, runtime: ToolRuntime[Context]) -> str:
    """Save a lasting fact about the user (name, classes, preferences, goals) for future conversations."""
    namespace = (runtime.context.user_id, "memories")
    runtime.store.put(namespace, str(uuid.uuid4()), {"fact": fact})
    return "Saved."


@dynamic_prompt
def prompt_with_memories(request: ModelRequest) -> str:
    namespace = (request.runtime.context.user_id, "memories")
    facts = [item.value["fact"] for item in request.runtime.store.search(namespace)]
    return build_system_prompt(facts)

runtime is hidden from the model, just like our closure. The model only sees fact.

Framework version: the agent

store = InMemoryStore()
fw_agent = create_agent(
    MODEL,
    tools=[remember],
    middleware=[prompt_with_memories],
    checkpointer=InMemorySaver(),
    store=store,
    context_schema=Context,
)


def fw_chat(user_id, thread_id, text):
    result = fw_agent.invoke(
        {"messages": [HumanMessage(text)]},
        {"configurable": {"thread_id": thread_id}},
        context=Context(user_id=user_id),
    )
    return result["messages"][-1].text


print(fw_chat("ana", "ana-homework", "Hi, I'm Ana. I'm taking DS 250 and I prefer R over Python."))
print(fw_chat("ben", "ben-homework", "I'm Ben. I'm a Python person, and I'm in DS 350."))
print(fw_chat("ben", "ben-chat-2", "What do you know about me?"))

What the framework doesn’t do

Ours Threads keyed by (user_id, thread_id). Ben can’t open Ana’s "homework".

Checkpointer Threads keyed by thread_id alone. Your app has to make sure a user only uses their own thread IDs.

Here we prefix them ("ana-homework"). In a real app, check who owns the thread before calling the agent.

Stage 6: One File per User

The store is hard to see

Invisible Each fact is a separate row in RAM. Ana can’t open it.

Append-only She changes her mind, and it keeps both “prefers R” and “switched to Python”.

Gone It disappears when the Python process ends.

Simpler: one plain text file per user. Readable, editable, and it lasts. (Claude Code’s CLAUDE.md works the same way.)

The server enforces who’s who

  • Same two halves, split differently. Write: the model decides, so it gets the MCP write tools from 1.7. Read: the app’s job. If reading were a tool, the model could forget to check.
  • Isolation moved: Stage 5 baked user_id into the tool. Here the server can only see Ana’s folder, so it can’t write to Ben’s no matter what anyone types.

Stage 6: one server per user

from langchain.mcp import MCPAdapter

MEMORY_ROOT = "/content/memories"
WRITE_TOOLS = ("write_file", "edit_file")   # the only filesystem tools the model needs here
checkpointer = InMemorySaver()
file_agents = {}   # user_id -> agent


async def get_file_agent(user_id):
    if user_id in file_agents:
        return file_agents[user_id]

    folder = f"{MEMORY_ROOT}/{user_id}"
    os.makedirs(folder, exist_ok=True)
    path = f"{folder}/memory.md"

    # The server can only touch the folders listed at the end of args: this user's folder, nothing else.
    config = {"mcpServers": {
        "memory": {"command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", folder]},
    }}
    async with MCPAdapter(config) as adapter:
        tools = [t for t in await adapter.list_tools() if t.name.endswith(WRITE_TOOLS)]
    ...

folder at the end of args is the only place this server can touch.

    file_agents[user_id] = agent
    return agent

Read is plain Python, not a tool. The model can’t forget to check.

Open Files → memories/. Ana’s file should say Python, not both. Edit it by hand, then ask again: the file is the memory.

What a file costs

Every prompt The whole file goes into every turn. As it grows, you pay for it, just like the thread in Stage 1.

Two writers Two chats editing at once can overwrite each other. A database handles that; one plain file doesn’t.

Colab resets /content is wiped with the runtime. Point MEMORY_ROOT at Google Drive if you want it to last.

Recap

Memory is what the app sends

  • One sentence to leave with: the model remembers nothing; memory is a decision about what the app sends.
  • Ask: where would per-user memory help your Project 1 agent? Where would it be a liability?
