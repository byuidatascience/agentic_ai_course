Overview

Create a powerful personal assistant from scratch

This project is meant to be useful and exciting, giving a solid introduction to the “Build” outcome.

It culminates in the realization that while it is cool to connect a lot of capabilities, building a reliable agent takes more thought, planning, and assessment. It sets the scene for the following units on diagnostics, context engineering, and architectural design.

Students will be given a zip collection of files documenting the life of Sam Drab, which they can point to to build their agent. Giving this data gives a consistent environment, and most importantly, allows easy (and harmless) prompt injection attacks. They are meant to discover these by accident, and they should be apparent and humorous.

Approaching the due date, students are given final prompts to run that will invite the agent to post to Slack using Sam Drab’s information. It is the proof of completion.

Notes

The goal of this project is to create a highly enabled agent with little testing. It is alright if it only works sometimes and has little security measures. This helps the student see that giving an LLM power is not enough, and gives a good foundation for the following units, which will address these issues.

Completion is based on whether or not it uses the tools taught in this unit, including MCP, read/write to file system, API, and ReAct reasoning.

After creating the agent, a few following activities will be calculated to make their agent and poke holes in their implementation. This includes a prompt injection attack somewhere in provided files

They will start building this pretty early on in the first unit, adding things as they go along

Tell them early on in the course they are building a personal assistant

Upfront, tell them to explore and create something that would be useful to them

Let them know there will be leaderboards

As it nears closer, you can let them know that there are a few test prompts and a Canvas assignment, with completion standards based on “does it run”, not “how well it runs” (Tell them later so it doesn’t guide them at the start)

Leaderboards could include: - Most MCP’s connected - Most tools used in a single run (limited by the free tier tokens) - Most methods used - Funniest Canvas submission

The agent should be something they genuinely intended to use, that works in the demo and fails in real life. The gap between “I wanted this” and “I can’t rely on this” is the motivation engine for Units 2 and 3, and it only exists if the wanting is real.

Repository and setup

  • Students create their own repo. The agent lives where they own it; doubles as the portfolio artifact.
  • Test files ship as a ZIP to drop in, not a git clone. Cloning into the repo root gives thirty students nested repos and confusing git status, with no AI permitted to dig them out.
  • Wiring up the supplied files is the base skill — and it is the same skill that lets them connect their own files afterward.
  • Public repo + personal memory is a data collision. Portfolio competency 4.2.1 wants these public; memory holds resume, budget, possibly journal. Make it part of the base: memory lives in a gitignored directory, with a committed example_memory/ of fake data so the repo still demos. Ten minutes of instruction, and it teaches a habit most juniors learn the hard way.

The agent drops out of course content after Unit 1, but students will hopefully continue working on it of their own volition
