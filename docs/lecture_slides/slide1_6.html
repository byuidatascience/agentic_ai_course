What Actually Happened

Follow the code

The bot answers Ludwig, but every fact it needs lives in a system the chatbot team doesn’t own. Months ago, they hand-wrote a wrapper for each one.

The wrapper

# support_bot/wrappers.py · chatbot team · written in March
def check_outage(zip_code: str) -> str:
    """Check whether there is a known network outage in a ZIP code."""
    outages = network_ops_api.get("/outages", params={"zip": zip_code})
    if not outages:
        return "No known outages."
    return outages[0]["summary"]

Totally reasonable code. It worked for six months. The chatbot team wrote it by reading Network Ops’ API docs as they were in March.

Meanwhile, in another repo

// network-ops/OutageController.java · Network Ops team · shipped last week
@GetMapping("/outages")
public List<Outage> outages(
        @RequestParam(name = "postal_code", required = false) String postalCode) {  // was: "zip"
    return repo.findByPostalCode(postalCode);
}

Network Ops renamed a parameter: zip → postal_code. Different team, different language, different release schedule. Nobody told the chatbot team. Why would they? It’s their API.

Put them together

# support_bot/wrappers.py
def check_outage(zip_code: str) -> str:
    """Check whether there is a known network outage in a ZIP code."""
    outages = network_ops_api.get("/outages", params={"zip": zip_code})   # "zip" is ignored now
    if not outages:                                                       # postal_code=null -> []
        return "No known outages."
    return outages[0]["summary"]

No crash. No error. No hallucination. The model did exactly what it should: it trusted its tool. The tool was wrong.

Go back to the board. Whose guess was closest? “The model made it up” is the most common guess and it’s wrong: the model behaved perfectly.

It gets worse

Summit now wants the same three systems in three AI apps. 3 apps × 3 systems = 9 wrappers, all written and maintained by people who don’t own the systems they wrap. Add a fourth system and it’s 12.

The real problems

  1. You don’t own the code. Another team, another language, another release schedule.
  2. Integrations drift and break silently. A renamed field became a confident wrong answer.
  3. Every app × every system. Wrappers multiply.
  4. The wrong people maintain them. The team that knows the system isn’t the team keeping the wrapper alive.

Brainstorm

How would you make sure this never happens again?

With your partner, pick one idea and be ready to defend it.

  • You can’t control when Network Ops ships changes.
  • Three apps (and counting) need the same three systems.
  • Whatever you pick, someone has to maintain it. Who?

4 minutes. Expect: tests/monitoring on the wrapper, a shared company library, API versioning/contracts, “just tell us when you change it.” All reasonable. Push on the “who maintains it?” question until someone says “the team that owns the system.” That’s the door into MCP.

How It Actually Works

What “Model Context Protocol” means

Model

For AI models. The thing reading the tool list is an LLM, so descriptions are written for a model.

Context

Everything a model can use beyond its training: tools to call, resources to read, prompts to start from.

Protocol

Agreed-on rules for the messages. Like HTTP for web pages: any browser, any website. Any MCP client, any MCP server.

MCP standardizes the connection, not the tools. Network Ops decides what their tools do. MCP decides how everyone asks for them.

The data flow

Before step 1, the client already asked the server “what tools do you have?” (tools/list). That’s how the model knew check_outage existed. Two processes, one protocol in the middle. Neither side sees the other’s code.

What goes over the wire

Your agent → Network Ops

{"jsonrpc": "2.0", "id": 1, "method": "tools/list"}

Network Ops → your agent

{"jsonrpc": "2.0", "id": 1, "result": {"tools": [{
  "name": "check_outage",
  "description": "Check whether there is a known network outage in a postal code.",
  "inputSchema": {
    "type": "object",
    "properties": {"postal_code": {"type": "string"}},
    "required": ["postal_code"]
  }}]}}

Step 0: discovery. This reply is where the model learned about postal_code. When Network Ops renamed it, this message changed, and your agent got the new name for free. (Real messages, trimmed.)

What goes over the wire (continued)

Your agent → Network Ops

{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "check_outage", "arguments": {"postal_code": "83440"}}}

Network Ops → your agent

{"jsonrpc": "2.0", "id": 2, "result": {"content": [{
  "type": "text",
  "text": "Fiber cut reported at 9:15 PM. Crews on site, ETA 11:30 PM."}]}}

Steps 3 and 6: the call. Plain JSON. That’s why the server can be written in any language: Python, Java, TypeScript, it doesn’t matter. Anything that can read and write these messages can be an MCP server.

Two ways to connect

stdio: Friendly Neighborhood Spider-Man

  • Local. Lives on your machine
  • Swoops in when needed. The client launches the server, and it’s gone when the client quits
  • One per client. Other computers get their own (the Spider-Verse)
  • Found on GitHub or a package: python outage_server.py, uvx ..., npx ...

HTTP: Stark Industries

  • Remote. Lives on a server somewhere else
  • Always on. Already running before you connect
  • Serves many clients. Spin up more Iron Man suits when traffic grows
  • Found on a company’s website: https://docs.langchain.com/mcp

Hold on to these two: in the cloned repo, they’ll run the same server both ways.

Same server, two transports

stdio (Spider-Man) HTTP (Stark)
Server’s last line mcp.run() mcp.run(transport="http", port=8000)
Who starts the server your agent, as a subprocess the owner, and it keeps running
Your agent’s target Path("outage_server.py") "http://127.0.0.1:8000/mcp"
Clients per server one many
Where it can live your machine anywhere with a URL
Everyday examples filesystem, Blender, desktop apps Slack, GitHub, LangChain docs

Only the target changes in your code. The tools, the agent, and the ainvoke stay the same.

Like USB

  • You plug in a mouse. You don’t know how USB talks to it. It just works.
  • The mouse maker didn’t write a driver for your laptop. The laptop maker didn’t write support for their mouse.
  • Both followed the standard.

MCP is USB for AI tools: Network Ops builds the device (server), you build the laptop (agent), and the protocol is the port.

But USB keeps changing

The idea of USB never changed: one standard port, any device. The plug has come in five shapes, and your drawer is full of old cables to prove it.

MCP is already changing

Same idea, new plugs. Tutorials from last year use MultiServerMCPClient and a "transport" key; today it’s MCPAdapter. Learn the ideas (client, server, transport, tools list) and check the date on anything you copy.

Add the LangChain docs to your agent

Your Project 1 agent · main.py

import asyncio
from langchain.mcp import MCPAdapter

async def build_agent():
    async with MCPAdapter("https://docs.langchain.com/mcp") as adapter:
        docs_tools = await adapter.list_tools()
    return create_agent("google_genai:gemini-2.5-flash", docs_tools + my_tools)

async def get_response(agent, prompt: str) -> str:
    result = await agent.ainvoke({"messages": [{"role": "user", "content": prompt}]})
    return result["messages"][-1].text

async def main():
    agent = await build_agent()
    while True:
        prompt = input("Input: ")
        if prompt == "exit": break
        print(await get_response(agent, prompt))

if __name__ == "__main__":
    asyncio.run(main())

main becomes async too, and asyncio.run(main()) starts it. A script has no event loop until you start one. (Colab already had one, which is why plain await worked there.)
